Resolves the "已知局限" flagged in 系统设计文档.md §3.4 (混合检索关键词侧不具备大规模扩展性) — but scoped deliberately to Postgres only, per explicit user decision, since SQLite is positioned as small-scale/trial-only and doesn't need this.

**The original bottleneck had nothing to do with which relational DB Core API used.** `RetrievalPipeline._keyword_scores` (worker/src/pipelines/retrieval.py) pulled its candidate set from `vector_store.all(book_ids)` — i.e. ChromaDB, not Core API's SQL database at all — then rebuilt a `rank_bm25.BM25Okapi` index from scratch on every query. Switching Core API's backend from SQLite to Postgres (see [[mynexus_postgres_backend]]) changed nothing about this, because the keyword path never touched Core API's DB in the first place. This was explained to the user directly before implementing the fix.

**Two decisions the user made explicitly, both baked into the implementation:**
1. Only implement the GIN-index fix for Postgres — don't bother with SQLite FTS5, since SQLite deployments won't hit meaningful scale.
2. Do NOT give Worker direct database write access, even though Postgres's better concurrent-write handling would make it *technically* safe (removing the original SQLite-write-contention concern from [[mynexus_m2_decisions]]). The user was shown the counter-argument before deciding: that concern was never the only reason for "Worker computes, Core API persists" — the other reason (avoiding the same schema/write logic being reimplemented and kept in sync in both Go and Python) is completely independent of which database backend is used, and Postgres does nothing to fix *that* problem. Worker only gained a **read-only** call to a new Core API endpoint; all writes (chapters/chunks/task status) still go through the existing callback path, completely unchanged.

**Implementation:**
- `storage/postgres/migrations/0004_chunk_keyword_search.sql`: `chunks.content_tsv` is a `tsvector` **generated column** (`GENERATED ALWAYS AS (to_tsvector('simple', content)) STORED`), plus a `GIN` index on it. Postgres maintains this automatically on every INSERT/UPDATE — `BookService.SaveChunks`'s existing write path (reached only via Worker's completion callback, per the decision above) needed zero code changes. No SQLite equivalent file exists — this is intentionally backend-asymmetric now, unlike earlier migrations that were kept in lockstep.
- `BookService.KeywordSearch(query, bookIDs, topK)` (book_service.go): runs `SELECT id, book_id, ts_rank(content_tsv, plainto_tsquery('simple', ?)) ... WHERE content_tsv @@ plainto_tsquery(...) [AND book_id IN (...)] ORDER BY rank DESC LIMIT ?` — Postgres-only SQL (tsvector/GIN/ts_rank have no SQLite equivalent), so callers must gate on `cfg.Storage.Database == "postgres"`.
- `grpcserver.CoreAPIServer.KeywordSearch`: the gate lives here — returns gRPC `NOT_FOUND` immediately if not on Postgres, otherwise calls `BookService.KeywordSearch`. **This was originally built as an HTTP endpoint** (`InternalHandler.KeywordSearch`, `POST /internal/search/keyword`) the same day, then migrated to gRPC a few hours later as part of the broader Core API <-> Worker transport migration — see [[mynexus_grpc_migration]]. The gating logic and SQL didn't change, only the transport.
- Worker's `config.py` gained `storage_database` and `core_api_base_url` fields, parsed from the *same shared* `config.yaml` (`storage.database`, `server.internal_url`) that Core API itself reads — plus env var overrides (`MYNEXUS_STORAGE_DATABASE`, `MYNEXUS_SERVER_INTERNAL_URL`) mirroring Core API's own. `core_api_base_url` was originally an `"http://host:port"` URL; after the gRPC migration it's a bare `"host:port"` gRPC dial target pointing at Core API's *grpc* port (9090), not its HTTP port — see [[mynexus_grpc_migration]] for the full config-key rename/repurposing.
- `RetrievalPipeline._keyword_scores` branches: `postgres` → `_keyword_scores_gin` (calls `CoreApiClient.keyword_search`, normalizes returned `ts_rank` scores by dividing by max, same normalization style as the BM25 path so the 0.6/0.4 fusion weights stay meaningful) → falls back to the **unchanged** `_keyword_scores_bm25` if the call fails for any reason (gRPC `UNAVAILABLE`, `NOT_FOUND` on sqlite, etc. — same resilience philosophy as `_vector_scores`'s existing try/except degrade-gracefully pattern). `sqlite` → goes straight to `_keyword_scores_bm25`, unchanged from before.

**Verified without a live Postgres** (no local Docker/Postgres available this session): Go side — `go build`/`vet`/`gofmt` clean, curl-tested (back when this was still HTTP) that a SQLite-backed server correctly returned 501; after the gRPC migration, the equivalent gate (`NOT_FOUND`) wasn't re-tested standalone but the gating code itself is untouched by the transport change. Python side — `ast.parse` syntax check clean; originally verified the HTTP version's request/response parsing and unreachable-host fallback with a throwaway mock server; after the gRPC migration, the full ingest/search/chat flow was re-verified end-to-end (see [[mynexus_grpc_migration]]), though that re-verification used a SQLite backend (Postgres unavailable), so it exercises the *fallback-to-BM25* path, not the actual GIN query. **Still not verified**: the actual `tsvector`/`GIN`/`ts_rank` SQL running against a real Postgres instance — the migration SQL is standard, well-documented Postgres syntax but wasn't executed against a live server this session. If a Postgres instance becomes available, that's the one remaining gap to close.

See also [[mynexus_postgres_backend]] (the underlying dual-backend storage work this builds on), [[mynexus_m2_decisions]] (the "Worker computes, Core API persists" principle this deliberately did NOT relax, despite the opportunity Postgres created), and [[mynexus_grpc_migration]] (the transport-layer change this RPC's HTTP-era implementation was migrated into later the same day).
