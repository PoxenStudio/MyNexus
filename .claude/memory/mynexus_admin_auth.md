Added real admin authentication to Core API + web-ui, resolving the "auth is enforced-when-present, not mandatory" gap ([[mynexus_known_gaps_and_conflicts]]) and building the previously-deferred end-user chat page.

**Session-based login, not JWT.** `core-api/internal/auth/session.go`'s `SessionManager` is an in-memory `map[sessionID]{userID, expiresAt}` (24h fixed TTL, no sliding renewal) — same "single-process-per-NAS, no Redis" pattern as `middleware.RateLimit`. Deliberately not JWT: `auth.jwt_secret` in config is still unused dead code (see [[mynexus_known_gaps_and_conflicts]]) — Cookie/Session matches how MyBooks itself does auth ([[mynexus_m2_decisions]]'s corrected assumption), so admin login followed the same style rather than introducing a second auth mechanism.

**Default admin account is seeded, not hardcoded as a bypass.** `admin_users` table (new migration `0002_admin_users.sql`, both sqlite/postgres — see [[mynexus_migration_versioning]] for why this had to be a *new* file, not an edit to `0001_init.sql`). `service.AdminUserService.EnsureDefaultAdmin()` runs in `main.go` right after opening the store: if `admin_users` is empty, inserts `username=admin, password_hash=bcrypt("admin")`. Idempotent — safe on every boot. Passwords use `golang.org/x/crypto/bcrypt` (already an indirect dependency via gin's deps, promoted to direct via `go mod tidy`).

**`middleware.RequireAuth` replaced `middleware.APITokenAuth`.** Old behavior: token validated *if present*, otherwise request passed through unauthenticated. New behavior: every `/api/v1` route (except `POST /auth/login` and `POST /auth/logout`, which can't require what they're establishing) requires EITHER a valid `mnx_session` cookie OR a valid `Authorization: Bearer mnx_...` API token — whichever is present is checked; a route is only reachable with at least one valid credential. This is intentionally an "either" gate, not "both": browser admin-UI traffic uses the session, service/automation traffic (and anything hitting the API directly, e.g. scripts) uses a Token from the unchanged Tokens admin page. Verified via curl: unauthenticated → 401; bad login → 401 with generic message (doesn't reveal whether the username exists); valid session → 200 on `/system/stats`; valid token with no cookie → 200 on the same route; wrong old-password on change-password → 401; correct change-password → 204 then old password stops working, new one logs in.

**`chat.enabled` config gates the conversation feature end-to-end.** New `Config.Chat.Enabled` (yaml `chat.enabled`, env `MYNEXUS_CHAT_ENABLED`, default `true`). Backend: `middleware.RequireChatEnabled` wraps the `/chat/*` route group, returns 403 when off. Frontend: `GET /api/v1/system/config` exposes `{chat_enabled}`; `stores/appConfig.ts` fetches it; the router's `beforeEach` guard redirects away from `/chat` if disabled, and `AppLayout.vue` hides the nav link. Verified via curl with `MYNEXUS_CHAT_ENABLED=false`: `/system/config` reports `false`, `/chat/sessions` returns 403.

**The chat page lives *inside* the authenticated admin web-ui, not as a separate public-facing page.** This was a deliberate reading of an ambiguous request ("会话页面" / "前端对话页面") — since the whole feature request was scoped entirely around admin-backend concepts (login, password change, token management), the natural interpretation was "give the existing chat/QA backend (built in M3 but never given a UI) a page inside the same authenticated app," not "build a second, publicly-reachable, unauthenticated chat product." `web-ui/src/views/ChatView.vue`: session list + message thread + streaming input, using `api/chat.ts`'s `streamCompletion()` (raw `fetch` + `ReadableStream`, not axios — axios doesn't expose incremental SSE chunks in the browser) against the already-existing `/chat/completions` (SSE) and `/chat/sessions*` endpoints from M3. If a future request wants this to be a separate anonymous-access surface instead, that's a materially different feature (its own auth model, likely no admin session requirement) — don't assume this ChatView already covers that case.

**CORS had to change for cookies to work cross-origin.** Session auth relies on browser cookies, which browsers refuse to send/accept cross-origin when the server responds `Access-Control-Allow-Origin: *` — wildcard and credentialed requests are mutually exclusive per the Fetch spec. `middleware.CORS` (`cors.go`) now reflects the request's actual `Origin` header back (instead of literal `*`) whenever `cors_origins` is configured as `["*"]`, and always sets `Access-Control-Allow-Credentials: true`. `web-ui/src/api/client.ts`'s axios instance now sets `withCredentials: true` globally. Verified end-to-end through the real Vite dev-proxy path (not just direct-to-Core-API curl) — login/me/config all worked through `localhost:3000` → proxy → `localhost:8080`.

**Not done / open questions:**
- No "forgot password" or account-recovery path — if the admin password is lost, the only way back in today is to manually clear the `admin_users` row (or the whole DB) so `EnsureDefaultAdmin` reseeds `admin/admin` on next boot.
- Only a single admin account is supported (no multi-user, no roles) — this matches the project's private single-operator framing so far, not evaluated as a gap.
- Session cookie is set `Secure: false` unconditionally (`auth_handler.go`'s `setSessionCookie`) — fine for typical NAS HTTP-only access, but if a deployment fronts Core API with HTTPS, the cookie still isn't marked `Secure`. Not currently configurable; would need a `server.behind_tls` or similar config flag if that becomes a real deployment shape.
- Rate limiting (`middleware.RateLimit`, unrelated pre-existing IP-based limiter) is NOT login-attempt-aware — there's no login-specific brute-force lockout beyond the generic 20 req/s per-IP cap.
