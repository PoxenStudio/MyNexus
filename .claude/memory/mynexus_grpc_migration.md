Replaced every `/internal/*` HTTP endpoint between Core API (Go) and Worker (Python) with gRPC, per explicit user request to minimize middleware/kernel overhead on that link. Scope is deliberately narrow: **only the Core API <-> Worker leg changed.** The browser <-> Core API leg is untouched — `POST /api/v1/chat/completions` still returns `text/event-stream` SSE to the browser; Core API just now sources those SSE frames from a gRPC server-streaming call to Worker instead of relaying raw HTTP bytes. No gRPC-Web/Envoy was introduced on the browser side (that would add middleware, not remove it).

## Why gRPC here reduces overhead

- One persistent HTTP/2 connection per direction (Core API -> Worker, Worker -> Core API) instead of a new HTTP/1.1 TCP handshake per request.
- Binary protobuf instead of JSON marshal/unmarshal on every call.
- Chat streaming is a first-class gRPC server-streaming RPC instead of hand-rolled SSE-line parsing over an HTTP body (`bufio.Scanner` + string prefix matching, removed from `chat_handler.go`).

## Contract: proto/mynexus.proto

Single source of truth, two services (the relationship is bidirectional — each side is simultaneously a gRPC client of the other's service and a server of its own):
- `WorkerService` (Worker implements, Core API calls): `TriggerIngest` (fire-and-forget, returns immediately, Worker processes in a background thread), `Search` (unary), `Chat` (server-streaming).
- `CoreApiService` (Core API implements, Worker calls): `ReportProgress`/`ReportComplete`/`ReportFail` (replace the old HTTP callbacks from [[mynexus_m2_decisions]]), `KeywordSearch` (Postgres-only, see [[mynexus_keyword_search_gin]] — that feature was built as HTTP first, then migrated to gRPC as part of this same session's work).

## Generated code is committed, not built at container build time

Deliberately did NOT add `protoc`/`grpcio-tools` as a Docker build-time or runtime dependency — that would add a heavier toolchain to both images for something that only needs to run when the `.proto` changes. Instead:
- Go stubs generated into `core-api/internal/grpcapi/mynexuspb/` (`mynexus.pb.go`, `mynexus_grpc.pb.go`), imported as a normal Go package.
- Python stubs generated **flat into `worker/src/`** (`mynexus_pb2.py`, `mynexus_pb2.pyi`, `mynexus_pb2_grpc.py`), NOT into a subpackage — the generated `mynexus_pb2_grpc.py` does an unqualified `import mynexus_pb2`, which only resolves automatically if the generated files sit directly in a directory that's already on `sys.path`. Since `worker/src` is exactly that directory (the CLI-testability convention runs everything as `python3 -m package.module` from `worker/src`, see [[mynexus_worker_cli_testable]]), putting them flat there was the simplest fix — no `sys.path` hacking needed, no `__init__.py` added (would have broken the existing namespace-package convention).
- Both generated by the Go plugins (`protoc-gen-go`, `protoc-gen-go-grpc`, installed via `go install ...@latest` into a scratch `GOBIN`) invoked *through* `python -m grpc_tools.protoc` (which bundles its own `protoc` binary via pip, since no system `protoc` was available) — `grpc_tools.protoc --plugin=protoc-gen-go=<path> --plugin=protoc-gen-go-grpc=<path> --go_out=... --go-grpc_out=...` for Go, plain `--python_out/--grpc_python_out/--pyi_out` for Python.
- To regenerate after a proto change: reinstall the two Go plugins if missing, `pip install grpcio-tools==1.68.1` (see version note below) in a **throwaway venv**, then rerun both `grpc_tools.protoc` invocations shown above from the repo root with `--proto_path=proto`.

## The protobuf version pin is load-bearing — don't casually bump it

The base/shared Python environment this project's `worker/src` runs against (no dedicated venv — same pattern as always in this session) already has `chromadb` installed, which transitively requires `protobuf<7` (via `opentelemetry-proto`/`googleapis-common-protos`). The latest `grpcio-tools` (1.83.0 at the time) bundles `protobuf==7.35.1`, which — if used to generate the `.proto` stubs — produces gencode that refuses to load against a `<7` runtime (`VersionError: gencode 7.35.1, runtime 6.33.6, runtime version cannot be older than gencode`). Fix: **generate with `grpcio-tools==1.68.1`** (bundles `protobuf 5.29.6`, safely below 7) in an isolated one-off venv — never install `grpcio-tools` into the shared base environment, since its dependency resolver will happily upgrade `protobuf` there and break chromadb's import chain. This actually happened once during this session (accidentally `pip install`ed grpcio-tools globally, protobuf jumped to 7.35.1, `import chromadb` still worked at that moment but the underlying conflict was real) — caught before it caused a difficult-to-diagnose failure, fixed by uninstalling grpcio-tools from the shared env and downgrading protobuf back to `6.33.6` (matches `worker/requirements.txt`'s `protobuf>=5.29,<7` pin) before doing anything else. `worker/requirements.txt` now pins `grpcio>=1.68,<2.0` and `protobuf>=5.29,<7` for the same reason — don't widen that upper bound without checking chromadb's current constraint first.

## Worker's network entrypoint changed completely

`worker/src/server.py` used to be a FastAPI+uvicorn app; it's now a plain `grpc.server(ThreadPoolExecutor(...))` running `WorkerServicer`. FastAPI/uvicorn/pydantic were dropped from `requirements.txt` entirely (nothing else in `worker/src` used them). `TriggerIngest`'s fire-and-forget semantics are preserved with a plain `threading.Thread(daemon=True)` spawned inside the handler — mirrors what FastAPI's `BackgroundTasks` did under the hood, no framework needed for it.

`IngestionPipeline.run()`'s signature dropped its `callback_base_url` parameter — Worker no longer receives Core API's address per-request; it dials a statically-configured address instead (see next section). New `grpc_client.py`'s `CoreApiClient` wraps a single persistent `grpc.insecure_channel` and is constructed once per pipeline instance (`IngestionPipeline.__init__`, `RetrievalPipeline.__init__`), reused across every call — this is the actual point of the migration (one channel, not one connection per request).

## Config: two new/repurposed keys, shared config.yaml, no scheme prefix

- `server.grpc_port` (new, Go-only, default `9090`): Core API's own gRPC listen port. Separate from `server.port` (8080, browser-facing HTTP, untouched).
- `server.internal_url` (repurposed, Python-only now — Go no longer reads this field at all): Worker's gRPC dial target for calling Core API back. Value format changed from `"http://localhost:8080"` to a bare `"host:port"` authority like `"localhost:9090"` — **no scheme prefix**, and note it now points at the *grpc* port (9090), not the old HTTP port (8080).
- `worker.url` (repurposed, Go-only): Core API's gRPC dial target for calling Worker. Same format change, `"http://localhost:8001"` -> `"localhost:8001"`.
- docker-compose.yml: `MYNEXUS_SERVER_INTERNAL_URL=core-api:9090` moved to the **worker** service's environment only (Core API itself doesn't consume this key anymore — removed from core-api's own env block); `MYNEXUS_WORKER_URL=worker:8001` on core-api's environment, both without `http://`.
- This is the same "shared config.yaml, each side reads only the keys it cares about" pattern already established for `embedding`/`llm`/`splitter` (Worker-only sections Go's config.go never declared fields for) — nothing new here, just applied to the new grpc keys.

## What did NOT change

- The "Worker computes, Core API persists" principle from [[mynexus_m2_decisions]] — still true, gRPC is just a different transport for the same calls. Worker still has zero database credentials or direct DB access of any kind (confirmed again during the keyword-search feature earlier the same day — [[mynexus_keyword_search_gin]]).
- SSE contract to the browser (`web-ui/src/api/chat.ts`'s parsing logic) — `chat_handler.go` now builds identical-shaped `{"choices":[{"delta":{"content":...}}]}` / `{"choices":null,"citations":[...]}` JSON frames itself from gRPC `ChatEvent`s, rather than relaying Worker's raw SSE bytes, but the wire format the browser sees is unchanged. Zero web-ui changes were needed.
- Worker's outbound calls to actual LLM/embedding providers (OpenAI/Ollama) — still plain HTTP via `util/http.py::urlopen`, untouched. gRPC only applies to the Core API <-> Worker link, not Worker's external provider calls.

## Verified end-to-end (no live Postgres needed for this one — pure transport-layer testing)

Ran both services as separate local processes (matching the Makefile's `dev-up` convention of both processes sharing the repo root as CWD — an earlier manual test run from `worker/src` as CWD produced a relative-file-path mismatch that looked like a bug but was purely a test-harness artifact, not a regression) and, using `worker/tests/mock_openai_server.py` to stand in for OpenAI:
- Full book import: upload -> `TriggerIngest` (gRPC) -> `ReportProgress` x4 (parsing/cleaning_done/splitting_done/embedding, all via gRPC, stages_log populated correctly — see [[mynexus_task_log_and_audit]]) -> `ReportComplete` (gRPC) -> task `completed`, book `ready`, chapter saved. Confirmed via `GET /api/v1/tasks/{id}` and `GET /api/v1/books/{id}`.
- Hybrid search: `POST /api/v1/search/hybrid` -> Core API's gRPC `Search` call to Worker -> correct result with book/chapter titles enriched.
- Chat streaming: `POST /api/v1/chat/completions` -> Core API's gRPC `Chat` call to Worker -> streamed character-by-character SSE deltas correctly reassembled and relayed to the curl client, terminated by a citations frame then `[DONE]`.
- Also individually smoke-tested via a raw grpc Python client: unary `Search` with no results, `TriggerIngest` fire-and-forget returning immediately, and streaming `Chat` (confirmed multi-chunk streaming mechanics work even before the full end-to-end test).

Not tested: TLS/mTLS on the gRPC channels (both sides use `insecure.NewCredentials()`/`grpc.insecure_channel` — fine for same-Docker-network traffic, would need real credentials if this ever crossed an untrusted network boundary, which the current architecture doesn't do).
