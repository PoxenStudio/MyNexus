# MyNexus 开发技术文档

> 版本：v0.1
> 适用阶段：项目初始化、开发落地、迭代实施
> 依据文档：需求文档 / 系统设计文档

---

## 1. 文档目的

本文档的目标不是重复需求说明，而是面向实际开发，给出一套可直接执行的项目实施方案，帮助团队在开发过程中明确：

- 项目应该如何分层拆解；
- 每个模块的职责边界是什么；
- 接口、数据模型、配置项如何约定；
- 开发顺序应该如何安排；
- 哪些内容先做、哪些内容后做。

本文档适用于后端开发、前端开发、测试、部署和项目管理人员共同使用。

## 2. 项目目标与开发原则

### 2.1 项目目标

MyNexus 的开发目标是构建一个面向电子书与知识管理场景的“书籍知识库化”系统，核心能力包括：

- 支持电子书上传与入库；
- 提取书籍元数据与正文结构；
- 对内容进行切片、索引与向量化；
- 提供检索与自然语言问答能力；
- 对外暴露标准 Web API。

### 2.2 开发原则

1. 先实现可用的最小闭环，再扩展能力。
2. 优先保证 NAS 友好，避免资源占用过高。
3. 模块解耦，能力节点可替换。
4. 数据结构和接口必须先定义清楚，再进入开发。
5. 所有功能都要可追踪、可重试、可观测。
6. 代码中避免无意义注释，优先用清晰命名和简洁实现。
7. 只在关键逻辑处保留必要注释，避免堆砌重复说明。

## 3. 技术选型

### 3.1 总体架构

项目采用“控制框架层 + 能力节点层 + 前端展示层”的三层架构：

- Core API：负责 API 暴露、鉴权、任务调度、元数据管理。
- Worker：负责文档解析、内容清洗、切片、向量化、检索与问答。
- Web UI：提供管理后台与问答页面。

### 3.2 推荐技术栈

| 层级 | 推荐技术 | 说明 |
|---|---|---|
| API 服务 | Go + Gin | 轻量、性能好，适合 NAS 部署 |
| AI 能力层 | Python + FastAPI | 适合 NLP/向量/LLM 相关能力集成 |
| 前端 | Vue 3 + TypeScript + Vite | 适合中小型后台和问答界面 |
| 数据库 | SQLite（初期）/ PostgreSQL（后续） | 初期优先 SQLite，降低部署复杂度 |
| 向量库 | ChromaDB / pgvector | 初期建议 ChromaDB，后续可扩展 |
| 容器部署 | Docker Compose | 满足轻量部署与 NAS 场景 |

### 3.3 版本策略

- MVP 阶段：支持 EPUB / TXT，基础元数据，全文检索，基础问答，基础 API。
- V1 阶段：支持更多格式、任务重试、后台管理、Token 管理。
- V2 阶段：支持更高级的检索与问答增强能力。

### 3.4 项目里程碑总览

建议将整个项目拆成 4 个核心 Milestone，分别对应一条可验证的价值链：

| Milestone | 目标 | 核心产出 |
|---|---|---|
| M1 | 项目骨架与基础服务 | 可启动的 Core API / Worker / Web UI，具备健康检查与基础配置 |
| M2 | 书籍导入与任务处理 | 支持上传、解析、入库、任务状态跟踪 |
| M3 | 检索与问答能力 | 支持切片、向量化、检索和基础问答 |
| M4 | 管理后台与可运维能力 | 完整后台、任务管理、Token 管理、部署与稳定性能力 |

这 4 个 Milestone 形成了从“可运行”到“可使用”再到“可运营”的演进路径。每个 Milestone 都建议有明确的验收标准，避免只完成代码而没有形成完整闭环。

## 5. 模块职责与边界

### 5.1 Core API 模块职责

Core API 负责“框架层能力”，主要包括：

- 接收 HTTP 请求；
- 做鉴权与权限判断；
- 管理书籍、任务、Token、会话；
- 负责与 Worker 的协同；
- 负责为前端提供统一 API。

Core API 不应承担复杂的文档解析与模型推理逻辑。

### 5.2 Worker 模块职责

Worker 负责“能力节点层”，主要包括：

- 解析上传文件；
- 清洗文本；
- 拆分章节和块；
- 调用 Embedding 服务；
- 执行混合检索；
- 调用 LLM 完成问答生成。

### 5.3 Web UI 模块职责

Web UI 负责：

- 展示书籍列表与详情；
- 提供问答会话交互；
- 管理任务状态；
- 管理 API Token；
- 支持配置与系统状态查看。

## 7. API 设计规范

### 7.1 通用规范

- 所有对外接口统一前缀：`/api/v1`
- 所有内部接口统一前缀：`/internal`
- 鉴权统一使用 `Authorization: Bearer <token>`
- 统一使用 JSON 响应结构

建议响应结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

### 7.2 对外接口建议

> 完整、权威的接口路径与请求/响应体定义见 [系统设计文档.md](./系统设计文档.md) 第 6 章，本节仅列出概要，避免维护第二份接口清单造成分歧。

#### 书籍管理

- `POST /api/v1/books/import`（上传）/ `POST /api/v1/books/import-url`（URL 导入）
- `GET /api/v1/books` / `GET /api/v1/books/{id}` / `PUT /api/v1/books/{id}` / `DELETE /api/v1/books/{id}`
- `GET /api/v1/books/{id}/chunks`（分块预览）
- `POST /api/v1/books/{id}/rebuild`（重新入库）

#### 任务接口

- `GET /api/v1/tasks` / `GET /api/v1/tasks/{id}` / `GET /api/v1/tasks/{id}/stream`
- `POST /api/v1/tasks/{id}/retry` / `POST /api/v1/tasks/{id}/cancel`

#### 检索接口

- `POST /api/v1/search/hybrid`
- `GET /api/v1/search/metadata`

#### 问答接口

- `POST /api/v1/chat/completions`
- `GET /api/v1/chat/sessions` / `GET /api/v1/chat/sessions/{id}` / `DELETE /api/v1/chat/sessions/{id}`

#### 系统接口

- `GET /api/v1/system/health`
- `GET /api/v1/system/stats`

### 7.3 Core API ↔ Worker 内部通信

**（2026-08-05 更新）** 已从 HTTP 迁移为 gRPC，详见 docs/系统设计文档.md §1.3、§6.7 与 `proto/mynexus.proto`：
- `WorkerService.TriggerIngest` / `Search` / `Chat`（Worker 实现，Core API 调用）
- `CoreApiService.ReportProgress` / `ReportComplete` / `ReportFail` / `KeywordSearch`（Core API 实现，Worker 调用）

## 8. 关键流程设计

### 8.1 上传与入库流程

1. 前端上传文件；
2. Core API 接收文件并保存到本地目录；
3. Core API 写入 books / tasks 记录；
4. Core API 将任务投递给 Worker；
5. Worker 执行解析、清洗、切片、向量化；
6. Worker 回调 Core API 更新任务状态；
7. 前端根据任务状态显示处理结果。

### 8.2 检索流程

1. 前端发送查询；
2. Core API 调用 Worker 的检索接口；
3. Worker 执行向量检索与 BM25 检索；
4. 将结果进行 Rerank；
5. 返回章节、片段、得分与引用位置。

### 8.3 问答流程

1. 前端发送问题；
2. Core API 传递 book_ids、上下文和会话信息；
3. Worker 根据检索结果构造 prompt；
4. 调用 LLM 生成回答；
5. 将输出和 citations 一并返回给前端。

## 10. 实现计划（按里程碑落地）

### 10.1 先行约定：接口契约优先

在任何开发开始前，必须先完成以下 5 项约定，避免再次出现“服务提供方和调用方对接口理解不一致”的问题：

1. 明确 MyNexus 对外提供的 API 版本与路径规范。
2. 明确 MyBooks 作为调用方时，应该如何调用导入、检索、问答和状态查询接口。
3. 明确请求体、响应体、错误码和状态码的标准格式。
4. 明确鉴权方式：建议使用 Bearer Token，避免依赖 MyBooks 的 Cookie 机制。
5. 明确任务生命周期：导入请求、任务创建、处理中、完成、失败、重试的状态流转。

建议将以上内容先整理成一份接口契约草案，作为开发第一步的输出物，并在团队内形成共识后再开始编码。

### 10.2 里程碑 1：项目骨架与基础服务

目标：完成最小可运行工程。

交付内容：

- Go 服务骨架：基于 **Gin** 的分层路由（api/handler/middleware/dto）、`config.yaml` + 环境变量加载、健康检查接口。
- Python Worker 骨架：**FastAPI** 服务、`nodes/pipelines/schemas` 基础目录结构。
- Vue 前端骨架：**Vue 3 + TypeScript + Vite**，基础布局、路由、API 封装（Axios）。
- 数据库初始化脚本与迁移脚本（SQLite，按系统设计文档 5.2 DDL 建表）。
- Docker Compose 可启动的最小部署环境。

验收标准：

- 启动 Core API 后可访问健康检查接口，且已按 config.yaml 加载配置、SQLite 数据库文件按迁移脚本初始化。
- 启动 Worker 后可访问 FastAPI 提供的内部健康检查接口。
- 前端可打开基础页面（Vue 路由可跳转，非纯静态 HTML）。
- 本阶段不实现鉴权逻辑；后续里程碑鉴权以 API Token 为主，JWT 用户登录方案见第 15 节说明。

### 10.3 里程碑 2：书籍导入与任务处理

目标：完成第一个可用闭环：上传文件 → 解析 → 入库 → 任务状态可见。

交付内容：

- 上传文件接口。
- 书籍元数据存储与任务记录。
- EPUB / TXT 解析器。
- 章节与正文内容落库。
- 任务状态查询接口。

验收标准：

- 上传单本 EPUB/TXT 后，可生成书籍记录和任务记录。
- 任务可从 pending 进入 processing，再进入 completed 或 failed。
- 解析结果可在后台看到章节和正文内容。

### 10.4 里程碑 3：检索与问答能力

目标：完成知识库化的核心能力。

交付内容：

- 文本切片与分块处理。
- Embedding 接入与向量存储。
- 混合检索接口。
- 问答接口与引用来源返回。
- 会话记录与上下文管理。

验收标准：

- 可根据关键词检索到相关章节片段。
- 可基于检索结果回答用户问题。
- 回答中包含引用来源，且可定位到章节或片段。

### 10.5 里程碑 4：管理后台与可运维能力

目标：形成可上线使用的系统。

交付内容：

- 书籍管理后台页面。
- 任务监控与失败重试能力。
- API Token 管理页面。
- 配置项与多语言支持。
- 日志、限流、错误处理与部署优化。

验收标准：

- 管理员可查看书籍列表、任务状态和处理日志。
- 可创建、查看、吊销 API Token。
- 系统可在 NAS 环境下稳定运行。

### 10.6 实施原则

1. 先定义接口，再写实现。
2. 先实现最小闭环，再扩展能力。
3. 每个里程碑都必须有可验证输出，而不是只完成“代码写了但没有完成闭环”。
4. 对外接口必须保持版本化，后续扩展时优先兼容旧版本。
5. 所有任务都要有明确的输入、输出和验收条件。

## 13. 部署方案

### 13.1 初期部署

推荐使用 Docker Compose，部署结构如下：

- `core-api`：运行 Go 服务；
- `worker`：运行 Python 服务；
- `web-ui`：提供静态页面；
- `data/`：持久化数据目录。

### 13.2 NAS 适配建议

- 默认只开启一个 Worker 并发任务；
- 默认内存占用控制在较低范围；
- 上传文件大小限制需明确；
- 避免在资源受限环境下同时跑太多模型服务。

## 16. 推荐的开发落地建议

建议以“先做最小可用闭环”为原则，优先完成以下 4 个最小目标：

1. 上传文件并入库；
2. 能对书籍内容做基础检索；
3. 能对书籍内容做基础问答；
4. 能通过 API 调用这些能力。

这 4 项完成后，系统就已经具备了最基本的产品价值，后续再扩展管理后台、任务调度、Token 管理和更强的检索能力。
