- [x] **数据库连接建立时自动检查表结构并创建/升级**（2026-08-05）。新增 `core-api/internal/storage/migrator.go`：连接建立后自动创建 `schema_migrations` 表记录已应用的迁移文件名，仅执行尚未应用过的迁移文件（按文件名排序，逐条语句在事务内执行），而不是像之前那样每次启动都重跑全部迁移文件的完整内容。sqlite、postgres 两个后端共用同一套逻辑。此前"改字段直接编辑 0001_init.sql"的做法（见 [[mynexus_m4_decisions]]）已被取代：以后新的表结构变更（包括含 `ALTER TABLE` 的变更）应新增编号迁移文件（如 `0002_xxx.sql`），两个后端各建一份并保持字段一致。已用本地 SQLite 文件验证：首次启动会创建并记录 `0001_init.sql`，二次启动确认被跳过（记录时间戳不变）。详见 memory 中的 `mynexus_migration_versioning`。

- [x] **EPUB 章节切分未对照 TOC（toc.ncx / EPUB3 nav）导致虚假章节已解决**（2026-08-05）。`worker/src/nodes/parsers/epub_parser.py` 原先把 spine（阅读顺序）里每一个非空文本的文档都当成一章，但 spine 里还包含封面、扉页（半书名页）这类不在目录里、只是恰好带点文字的前置页——实测《社会正义谬误》这本书的 `chapter0001.xhtml`（半书名页，正文只有书名两个字）就被当成了一整章「社会正义谬误」（138 字），摘要自然毫无内容可言。现在改为先用 `book.toc`（ebooklib 统一抽象了 EPUB2 的 `toc.ncx` 和 EPUB3 的 nav 文档）拿到发布方自己声明的章节列表（`_toc_titles`，递归展平 `Link`/`(Section, children)` 结构，按 href 去掉锚点+取 basename 做匹配，兼容 TOC 和 spine/manifest 之间的相对路径差异），只有 spine 里出现在 TOC 中的文档才算一章；没有 TOC 的书（少数没有 `toc.ncx` 的纯 EPUB2）自动退回原来"spine 里每个非空文档都是一章"的行为，不受影响。副作用是章节标题也变准了：原来标题取自文档内第一个 `<h1>/<h2>/<h3>`（经常只有"第一章"这种短标题），现在优先用 TOC 自带的完整标题（如"第一章 "机会平等"谬误"）。用真实上传的 `207d87c3-5a26-4df8-9535-a76c9b2a4b27.epub` 验证：章节数从 8（含一个虚假的半书名页"章节"）降到 7，标题全部变成 TOC 里的完整标题；另用一本英文 EPUB（Gutenberg 版《爱丽丝梦游仙境》）验证未引入回归——它的 TOC 本身就包含"Title Page"条目，所以正常保留，行为符合该书自己的 TOC 声明。**这只修复了解析器本身，已经入库的旧书（章节还是旧的错误切分）需要在书籍列表页点"重建"重新走一遍解析才能生效，不会自动回填。**

同一次修复里还顺带解决了两个用同一个 `soup.get_text("\n")` 调用暴露出来的问题，都是用 `worker/tests/inspect_chapter_summary.py --show-content` 揪出来的：① 这本书的标题普遍是"每个字单独包一个 `<b>` 标签"的排版写法（如 `<h1><b>译</b><b>者</b><b>序</b></h1>`，浏览器里正常显示一行"译者序"），但 `get_text("\n")` 不区分块级换行和行内相邻标签，把每个字都拆成单独一行传给了 LLM（"译\n者\n序"）；② EPUB 的脚注/尾注标记为 `<aside epub:type="footnote">`，语义上不属于正文阅读流，但旧代码会把整个文档（含 aside）一起 `get_text()`，导致大段英文文献引注原样混进正文——已确认这是本书"第一章"被截断到 12000 字后摘要质量差的主因之一（引注占了原文本很大比例）。现在改为 `_extract_text()`：先 `aside.decompose()` 去掉脚注块，再只在"叶子块级元素"（`p`/`div`/`h1`~`h6`/`li` 等里不再嵌套块级元素的那一层）之间插换行，块内的行内标签直接拼接。同一本书验证：「第一章」清洗后从 38124 字降到 13185 字（几乎全是被剔除的引注），且不再出现"第\n一\n章"这种拆字换行。③ 块内拼接后，脚注引用标记（`<sup><a epub:type="noteref"><img/></a></sup>`，本身无可见文字）周围源文件里的缩进换行（`\n\t`）会被当成真实文本节点原样拼进句子中间，肉眼看像是词语间多出一大段空格（其实只是一个 `\t` 被终端/编辑器撑开显示）——`_extract_text()` 里补了一步：块内 `get_text()` 后用 `re.sub(r"\s+", " ", text)` 把内部空白折叠成单个空格（`<pre>` 除外，那里的空白是内容本身不是排版噪音），跟浏览器渲染 HTML 空白的规则一致。同一本书「第一章」验证：38124 → 13185 → 13043 字，"实质意涵。在卢梭所展望"之间只剩一个空格，不再有制表符残留。
- [x] **章节总结不再截断长章节，改为按段落/句子边界切分后 map-reduce**（2026-08-05）。之前 `pipelines/summary.py` 用 `_MAX_CHAPTER_CHARS = 12000` 硬截断——超过这个长度的章节，后面的内容直接丢弃，不进 LLM。哪怕上面几条把无关噪音（脚注引注、排版空白）都清理掉之后，一本书里大多数章节（1.3万~1.9万字）依然会超过这个长度，被截掉章节结尾的一段。现在改为不截断：新增 `worker/src/util/text_split.py` 的 `split_into_segments(text, target_chars=10000, hard_limit_chars=12000)`——不超过 `hard_limit_chars` 的文本直接返回单段（绝大多数章节走这条路径，跟以前一样只有 1 次 LLM 调用）；超过的话，从 `target_chars`（10000 字）往后找最近一个"\n"（正文提取时每个源段落就是一行）作为切点，找到了就在那里切；找不到（说明这个段落本身就很长）就从 `hard_limit_chars` 往回找最近的句末标点（`。！？.!?`）切；两者都找不到（极端情况，比如一长串没有标点的列表）才在 `hard_limit_chars` 处硬切。`pipelines/summary.py` 的 `summarize_chapter()` 现在是章节内部的第二层 map-reduce：每段分别摘要（`_SEGMENT_PROMPT_TEMPLATE`，明确告诉模型"这是第 i/N 部分，不是全章，不要脑补没看到的内容"），再用 `_CHAPTER_REDUCE_PROMPT_TEMPLATE` 合并成一段完整章节摘要——跟"每章摘要合并成全书摘要"是同一个模式，只是多了一层。进度回调也相应从"已输出 N 字"改成"第 i/N 段，已输出 N 字"再到"正在合并 N 段摘要…"（`on_chars` 参数改名 `on_progress`，回调内容从字符数改成完整状态文案，任务监控/书籍详情页能直接展示）。用真实上传的《社会正义谬误》「第一章」（13043 字）端到端验证过，用本地 ollama（`qwen2.5:7b-instruct`）实际生成过摘要：自动切成 2 段（10075 + 2967 字，切点都落在句末），分段摘要 + 合并全流程走通，进度提示逐条打印。`worker/tests/inspect_chapter_summary.py` 同步更新，`--dry-run` 会把多段的每一段 prompt 和最终 reduce prompt 的形状都打出来，不需要真的调用 LLM 就能检查切分是否合理。
- [x] **重启/Worker 掉线后任务卡在"处理中"的问题已解决**（2026-08-05）。Worker 在自己的进程内存里跑一个任务（无持久化，见系统设计文档 §3.x「Worker 只算」），一旦 Core API 或 Worker 重启、或 Worker 进程中途崩溃，谁都不会再调用 `ReportProgress`/`ReportComplete`/`ReportFail` 把这个任务收尾，`pending`/`processing` 状态就会永远卡住（书籍详情页的"生成中"、任务监控页的"处理中"都不会再更新）。新增 `TaskService.ReconcileOrphaned(reason)`：把所有仍处于 `pending`/`processing` 的任务标记为失败，两处调用：① Core API 启动时（`main.go`）无条件跑一次——任何在这之前留下的 `pending`/`processing` 任务，不管是本进程重启前的还是 Worker 重启前的，都已经没有人在追踪了；② 新增 `watchWorkerHealth` 后台协程，每 20 秒轮询一次 `WorkerClient`（`coordinator/worker_client.go` 新增了显式 gRPC keepalive 参数，10s ping/5s 超时，这样一个真的挂了的 Worker 能在秒级被 `TransientFailure` 捕捉到，而不是等到下一次业务调用才发现），一旦发现 Worker 不可达就立刻做同样的回收。回收时按 `grpcserver.ReportFail` 同样的规则处理书籍状态：ingest 任务失败会把书籍状态一并置为 `failed`，summarize 任务失败不动书籍状态。已知取舍：一次瞬时的 keepalive 丢包也会被判定为"不可达"从而误杀正在跑的任务，但失败的任务本来就能在任务监控页手动重试，代价小于任务永远卡死不可见。

## 已知的可扩展性限制

- [x] **混合检索的 BM25 关键词侧扩展性问题已解决（仅 Postgres 后端）**（2026-08-05）。`chunks` 表新增 `content_tsv tsvector` 生成列 + GIN 索引（`storage/postgres/migrations/0004_chunk_keyword_search.sql`，Postgres 自动维护，Core API 写入路径不用改代码），新增只读接口 `CoreApiService.KeywordSearch`（最初实现为 HTTP `POST /internal/search/keyword`，同日晚些时候随全面 gRPC 迁移改为 gRPC RPC，仅 postgres 后端可用，sqlite 返回 `NOT_FOUND`），`worker/src/pipelines/retrieval.py` 的 `RetrievalPipeline` 在 `storage.database == postgres` 时改为调用该接口（失败自动回退到原 BM25 逻辑），sqlite 后端行为不变（定位为小规模验证/试用场景，不做这个优化）。**明确决定：这次只给 Worker 加了只读查询能力，没有让 Worker 直连数据库写库**——"Worker 只算、Core API 统一持久化"这条架构原则的核心理由是避免同一套写入逻辑在 Go/Python 两边维护两份，这个理由与数据库并发能力无关，Postgres 解决不了"两套代码要保持同步"的问题，所以即使 Postgres 并发写入能力更强，也没有让 Worker 绕过 Core API 直接写 `chapters`/`chunks`/`tasks`。受限于本机没有可用的 Postgres/Docker 环境，未做真实 GIN 索引查询的端到端验证。详见 `mynexus_keyword_search_gin` memory 与系统设计文档 §3.4。
- [ ] **分块/Token 计数为字符数近似**，非真实分词器（无 tiktoken 依赖），对中文场景影响较小，对英文文本会高估 token 数量。
- [x] **BM25 的中文分词已从简单正则改为 jieba**（2026-08-05）。`worker/src/pipelines/retrieval.py` 的 `_tokenize` 原先每个汉字视为一个 token（`_TOKEN_RE`），现在用 `jieba.lcut` 按词切分，BM25 的词频统计能反映真实词语而不是单字，提升中文关键词检索相关性；只过滤掉不含任何"词字符"的纯标点/空白 token，其余不变。`jieba.setLogLevel`/`jieba.initialize()` 在模块导入时调用，把首次建词典树（约 1s）的开销放在 Worker 启动阶段而不是第一次搜索请求上。仅影响 SQLite 后端的现场建索引路径（见上一条 Postgres/GIN 已单独解决），已加入 `worker/requirements.txt`（`jieba>=0.42`）。
