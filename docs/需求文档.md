# MyNexus 需求文档

## 1. 项目背景

MyNexus 是面向个人电子书与知识管理场景的“书籍知识库化”系统，目标是将 MyBooks 与 MyReader 生态中的电子书内容，转化为可索引、可查询、可对话的知识资产。
* MyBooks (https://github.com/poxenstudio/mybooks)
* MyReader (https://github.com/poxenstudio/MyReader)

当前，MyBooks 和 MyReader 已经具备电子书管理与阅读体验能力，但仍缺少对书籍内容进行深度解析、结构化组织以及智能问答能力的系统支撑。MyNexus 的目标是为这些场景提供统一的内容解析、知识抽取、检索与开放接口能力。

## 2. 项目目标

### 2.1 核心目标

- 将上传的电子书文件转换为可检索、可问答、可扩展的知识库内容。
- 为 MyBooks / MyReader 提供统一的内容解析与知识服务能力。
- 通过自然语言交互，让用户能够对书籍内容进行高效问答与信息获取。
- 提供稳定、标准化的 Web API，支持第三方客户端接入。

### 2.2 业务价值

- 提升电子书的“可利用价值”，从单纯阅读内容升级为可搜索、可总结、可问答的知识资产。
- 降低用户在书籍内容查找与复习过程中的操作成本。
- 为后续的智能推荐、摘要生成、学习辅助、知识图谱等能力提供基础数据层。

## 3. 适用场景

- 个人知识库建设：将书籍内容转化为个人可检索知识库。
- 阅读辅助：在阅读过程中快速定位章节、重点内容和答案。
- 学习复盘：对书籍内容进行摘要、问答和知识回溯。
- 跨端集成：由 MyBooks 与 MyReader 发起内容查询、书籍解析、知识问答等服务调用。

## 4. 产品定位

MyNexus 的终极远景是成为一个**缩小版的私有化 Dify（通用知识库 RAG 引擎）**。
初期阶段，系统将以 MyBooks 作为主要数据源，把“打通电子书的解析与问答”作为首要里程碑来跑通基础能力；但在底层架构上，它将始终保持独立性。

具体定位为：

- 面向电子书与文档的深度解析与结构化入库引擎；
- 面向知识检索与自然语言问答的智能服务层；
- 面向开放生态（提供标准 API 鉴权）的 Web API 服务平台。

### 4.1 系统定位与数据流转 (多来源支持)

MyNexus 被定位为**独立的通用书籍知识中台**。虽然它是为 MyBooks 生态量身打造的核心组件，但**绝不与 MyBooks 强绑定**。系统必须支持来自多个来源的书籍入库（例如：MyBooks 推送、MyNexus 后台直接上传、第三方脚本通过 OpenAPI 导入等）。

数据流转与协同流程如下：

- **数据摄入层**：支持 MyBooks 通过 API 主动推送（作为主要来源），同时也支持用户在 MyNexus 管理后台直接手动上传电子书。
- **核心处理层**：MyNexus 负责接收书籍，统一进行内容解析、结构化入库、切片、向量化与提供智能问答服务。
- **服务输出层**：MyReader 等前端应用通过 MyNexus 提供的检索与问答 API，支撑阅读场景下的划词搜索、章节总结与智能问答。

可表示为：

[ MyBooks (主要) / MyNexus 后台直传 / 第三方 API ] → 上传或推送书籍 → MyNexus 中台 → 检索/问答服务 → [ MyReader / Web前端 ]

## 5. 用户角色

### 5.1 普通用户

- 上传、管理电子书；
- 查看书籍元数据与内容结构；
- 搜索书籍内容；
- 与书籍内容进行自然语言问答。
- 通过简洁的会话入口快速发起问答体验。

### 5.2 管理员

- 管理用户、上传文件和系统配置；
- 查看处理任务状态和系统运行指标；
- 管理索引、清理异常数据、调整策略配置。

### 5.3 第三方客户端

- 通过 Web API 调用 MyNexus 的解析、索引、检索和问答能力；
- 例如 MyBooks、MyReader 等前端客户端。

## 6. 功能需求

### 6.1 电子书上传与入库

#### 6.1.1 支持文件格式

系统需支持以下文件类型：

- EPUB
- PDF
- AZW3
- TXT
- DOC / DOCX

#### 6.1.2 上传能力

- 支持单文件上传与批量上传。
- 支持上传进度显示与任务状态跟踪。
- 支持断点续传或重试机制，避免大文件传输中断。

#### 6.1.3 解析与抽取

系统需自动识别并提取以下内容：

- 书名
- 作者
- 出版社
- 语言
- 出版日期
- ISBN
- 分类信息
- 标签
- 摘要
- 章节结构
- 正文内容
- 页码、段落、图片引用等必要元信息

#### 6.1.4 元数据标准化

- 对不同格式的电子书进行统一的元数据结构化输出。
- 对缺失字段提供默认值或空值占位。
- 对重复内容进行去重与归并。

### 6.2 内容结构化处理

#### 6.2.1 章节与段落拆分

- 将正文内容拆分为章节、段落、句子或块级单元。
- 支持按章节、页码、段落粒度进行检索与展示。

#### 6.2.2 目录与结构识别

- 自动识别目录结构、章节层级与正文顺序。
- 对缺少目录的文件提供 fallback 处理策略。

#### 6.2.3 内容增强信息

- 支持提取关键词、主题标签、章节摘要、重点片段。
- 可选支持实体识别、概念抽取、知识图谱关系识别。

### 6.3 索引与检索能力

#### 6.3.1 全文检索

- 支持全文关键词搜索。
- 支持按书籍、章节、段落范围进行过滤。

#### 6.3.2 元数据检索

- 支持按作者、出版社、标签、分类、语言、年份等字段检索。
- 支持组合条件查询。

#### 6.3.3 混合检索（Hybrid Search）

- 采用传统全文检索与语义检索结合的方式，提升检索准确性与召回能力。
- 传统检索可使用关键词、短语、通配符等方式，保障名称、术语和硬匹配结果的准确性。
- 语义检索可支持“意图检索”，例如用户输入“悲剧的根源”时，能检索到语义相关但不一定包含原词的内容。
- 支持重排机制（Reranking），将多个检索结果按照相关性重新排序，输出最优结果。
- 检索结果需返回章节、段落、片段摘要和位置信息，便于直接跳转到正文内容。

### 6.4 自然语言问答能力

#### 6.4.1 基础问答

- 支持用户以自然语言提问，例如：“这本书主要讲了什么？”
- 支持基于单本书籍、指定多本书籍或整个知识库进行问答。
- 支持按书籍范围限制问答上下文，避免跨库噪声干扰。

#### 6.4.2 参考片段返回

- 回答时需返回对应的参考内容片段或原文出处。
- 支持定位到具体章节、段落或页码位置。
- 对回答进行引用锚定（Citation/Grounding），便于用户查看来源并快速跳转。

#### 6.4.3 对话上下文与流式输出

- 支持连续追问，例如：“那作者的观点是什么？”、“再展开讲一下”。
- 对多轮对话提供上下文记忆与会话管理。
- 支持流式回答（Streaming），优先输出首条内容以提升交互体验。

### 6.5 Web API 能力

系统需提供统一的 Web API，供 MyBooks、MyReader 等客户端以及第三方系统接入调用。
对外提供的接口均需支持通过 **API Token (Bearer Token)** 的方式进行身份鉴权。

> 以下接口清单以 [系统设计文档.md](./系统设计文档.md) 第 6 章「API 接口详细设计」为准，本节仅做能力范围概述；具体路径、请求体/响应体以系统设计文档为唯一权威来源，避免多份文档各自维护一套接口清单导致不一致。

#### 6.5.1 书籍管理接口

- 上传书籍（本地文件 / URL 导入）
- 查询书籍列表、书籍详情（含章节结构）
- 更新书籍元数据、删除书籍
- 分块预览查询
- 触发重新入库（重新解析 / 切片 / 向量化）

#### 6.5.2 内容检索接口

- 混合检索接口（向量 + 关键词 + Rerank）
- 元数据检索接口

#### 6.5.3 问答接口

- 单本书 / 跨书问答接口（OpenAI 兼容格式，支持流式）
- 会话历史查询与删除

#### 6.5.4 任务与系统状态接口

- 任务列表查询、任务详情（各阶段耗时）
- 任务进度 SSE 推送、失败重试、取消
- 服务健康检查、系统统计

### 6.6 权限与安全

- **开放 API 鉴权（M1/M2 优先实现）**：支持为第三方客户端或脚本签发长期/可撤销的 API Token (如 Bearer Token)，以安全对外提供接入服务。MyBooks/MyReader 在集成初期以服务身份持有 API Token 调用 MyNexus，不依赖用户级 SSO。
- **用户鉴权（后续里程碑，方案待定）**：MyBooks 当前采用 Cookie/Session 认证，暂无 JWT 机制，因此"MyNexus 与 MyBooks 共享 JWT_SECRET 免登录互通"暂不成立。后续如需在 MyNexus 前端提供用户级登录/SSO，需与 MyBooks 侧确认改造方案（例如由 MyBooks 新增 JWT 签发接口，或 MyNexus 维护独立账号体系），在明确前 MyNexus 可先支持独立的用户名密码登录签发自身 JWT。
- 支持书籍级别的访问控制。
- 对敏感内容提供访问日志与审计能力。
- 对上传文件进行合法性检查与病毒扫描（可选）。

### 6.7 前端页面与管理后台

#### 6.7.1 用户前端页面

- 提供简洁易用的会话入口页面，支持快速发起问答。
- 页面应支持书籍内容搜索、问答输入、引用结果展示与会话历史查看。
- 支持在阅读场景下直接查看答案来源、章节位置与相关片段。
- 页面需支持移动端与桌面端适配，保证基础交互体验。

#### 6.7.2 后台管理页面

- 展示已入库书籍的列表，包括书名、作者、格式、状态、更新时间等信息。
- 支持对已入库内容进行删除、禁用、重建或重新触发知识库构建。
- 支持上传新的电子书文件，并查看上传任务及处理状态。
- 支持查看书籍解析结果、章节结构、元数据摘要和处理日志。
- 支持对失败任务进行重试或手动处理。

#### 6.7.3 管理后台操作能力

- 批量选择书籍并执行删除或重建操作。
- 对单本书籍执行重新构建、重新切片、重新向量化等操作。
- 对处理进度、失败原因和系统状态进行可视化展示。
- 为管理员提供必要的权限控制和操作审计记录。

#### 6.7.4 API Token 管理页面

- 提供 API Token 的创建与展示功能（为安全起见，完整 Token 仅在生成时显示一次）。
- 支持查看已签发的 Token 列表，包括别名/用途、创建时间、最后使用时间等。
- 支持对 Token 进行一键吊销（Revoke）或删除操作，以便在密钥泄露时快速止损。

## 7. 非功能需求

### 7.1 性能

- 单文件解析响应时间应满足日常使用场景要求。
- 大量书籍入库时需具备异步处理能力。
- 检索响应应保持在可接受范围内，尤其是中等规模知识库场景。
- 建议目标：单本约 10 万字的书籍，完成解析、切片、向量化和入库的整体流程控制在 30 秒内（本地 CPU 环境除外）。
- 建议目标：混合检索接口平均响应时间控制在 200ms 以内。
- 建议目标：流式问答首字输出延迟控制在 1 秒以内。

### 7.2 可扩展性

- 支持后续增加更多文件格式解析器。
- 支持接入不同的检索引擎和大模型服务。
- 支持水平扩展以处理更大规模知识库。
- 支持通过配置切换 Embedding 模型与 LLM 提供方，如 Ollama、OpenAI、DeepSeek 等。
- 必须提供支持多架构 (x86_64, arm64) 的轻量化 Docker 镜像，满足群晖、威联通、极空间等各类 NAS 设备的无缝部署。
- 考虑到 NAS 设备性能瓶颈，需支持并发与硬件资源限制策略，避免在解析大文件时引发 CPU 或内存占用过高，导致 NAS 宿主机卡顿。

### 7.3 稳定性

- 任务失败时应能记录错误日志并提供重试机制。
- 支持对异常文件进行隔离处理，避免影响整个系统。

### 7.4 可观测性

- 需具备日志记录、任务监控、性能指标、错误追踪能力。
- 支持服务运行状态与处理进度的可视化。

### 7.5 兼容性

- 支持主流桌面端、移动端及 Web 客户端访问。
- 与现有 MyBooks / MyReader 的数据模型尽量兼容。

### 7.6 多语言支持 (i18n)

- 系统需提供多国语言支持，包括前端界面交互、系统提示信息与后端接口响应。
- 必须支持的语言：简体中文（zh-CN）、繁体中文（zh-TW）和英文（en-US）。

## 9. 系统架构建议

### 9.1 插件化与可配置架构

由于用户的 NAS 硬件差异巨大（从低端 ARM 到高端 x86，从无独立算力到配有显卡），系统的核心模块必须采用**接口化/插件化设计**，支持通过配置文件（如 `config.yaml` 或环境变量）进行灵活切换：

- **向量算法 (Embedding)**：必须支持调用外部 API，同时也允许在有算力的机器上运行本地量化模型。
- **向量数据库 (VectorStore)**：必须设计抽象的存储层接口。默认自带轻量的纯本地实现（如 ChromaDB/Faiss），但也允许高端玩家配置连接到外部独立的 Qdrant、Milvus 等企业级向量服务。
- **大语言模型 (LLM)**：支持动态切换不同的模型提供商（OpenAI/Ollama/DeepSeek）、Base URL 和 API Key。
- **文档解析引擎 (Parser)**：支持针对不同格式配置不同的解析策略，例如在资源受限时可一键关闭耗时的 OCR，仅提取纯文本。

### 9.2 技术栈选型建议

鉴于系统的**主要部署目标为 NAS 设备**，硬件资源（CPU、内存）通常较为受限，且常基于 ARM 架构。因此，技术架构需在“开发效率”与“系统资源开销”间取得平衡，**推荐技术栈选型如下**：

- **后端开发语言**：
  - **方案 A（极致轻量，推荐）**：使用 **Go** 或 **Node.js** 作为核心 API 与调度层，占用极低内存。将文档解析等强依赖 NLP 的模块剥离为独立的轻量级 Python 微服务，按需调用。
  - **方案 B（开发效率优先）**：全栈使用 **Python (FastAPI)**。但需严格精简依赖包，弃用过度臃肿的 AI 框架，确保系统能在 1GB-2GB 内存环境的 NAS 下流畅常驻。
- **数据库/向量存储**：
  - 弃用较重的 PostgreSQL，**推荐使用 SQLite 作为关系型数据库**，搭配**轻量级的纯本地向量存储库（如 ChromaDB 或 Qdrant）**，实现“开箱即用”的零配置、低内存开销部署。
- **AI 模型策略**：
  - 考虑到 NAS 通常无高性能独立 GPU，默认的 Embedding 与对话大模型应**依赖外部云端 API**（如 DeepSeek、OpenAI、阿里云等）。仅当用户外挂具备 GPU 算力的设备时，再支持连接局域网内的 Ollama 服务。

MyNexus 可采用如下分层架构：

- 接入层：文件上传、用户请求、API 网关
- 处理层：解析器、索引器、向量/语义处理模块、问答服务
- 存储层：对象存储、关系数据库、全文索引引擎、向量数据库
- 服务层：对外暴露 Web API，供 MyBooks / MyReader 使用

## 11. 实施路线建议

### 第一阶段：基础解析与入库

- 完成上传与文件解析能力
- 建立基础书籍元数据与正文存储
- 实现基础全文检索
- 支持 EPUB / TXT 等基础格式的知识库化入库

### 第二阶段：智能检索与问答

- 引入内容分块、向量化与摘要能力
- 实现基于引用的自然语言问答接口
- 提供针对 MyBooks / MyReader 的调用接口
- 支持单本书与多本书问答

### 第三阶段：智能增强与生态扩展

- 增加语义检索与混合检索能力
- 支持更多格式（PDF / AZW3 / DOC）与 OCR 处理
- 支持更丰富的知识抽取、主题分析与知识图谱能力
- 提升 API 生态化能力与系统稳定性

## 12. 结论

MyNexus 的核心价值在于把“电子书”从静态阅读资源升级为“可检索、可问答、可集成”的知识资产。通过与 MyBooks 与 MyReader 的协同，能够形成一套完整的个人知识管理与智能阅读闭环。
