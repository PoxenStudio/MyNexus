# 系统部署说明

> 本文档持续维护中，覆盖当前已验证过的部署路径；未覆盖到的场景（如多实例横向扩展、K8s 部署）见文末「TODO」。

## 1. 系统组成

MyNexus 由三个自研服务 + 若干可选的外部依赖服务组成：

| 服务 | 语言/框架 | 职责 | 是否有状态 |
|---|---|---|---|
| `core-api` | Go + Gin | 唯一持有业务数据（书籍/章节/任务/对话/Token），对外提供 HTTP/SSE API，对内提供 gRPC（供 worker 回调） | 有状态（数据库） |
| `worker` | Python | 解析/清洗/分块/向量化/检索/LLM 问答的能力节点，接收 core-api 的 gRPC 调用触发任务，通过 gRPC 回调汇报进度 | 无状态（不落业务数据） |
| `web-ui` | Vue3 + TS + Vite | 管理后台前端（仪表盘/书籍/任务/Token/审计日志/设置/会话），构建后由 nginx 静态托管 | 无状态 |

三者的调用关系：浏览器 ⇄ `web-ui`（nginx）⇄ HTTP/SSE ⇄ `core-api` ⇄ gRPC（双向）⇄ `worker` ⇄ HTTP ⇄ Embedding/LLM 服务。

## 2. 依赖服务总览

| 依赖 | 必需性 | 默认选择 | 可替换为 | 配置项 |
|---|---|---|---|---|
| 关系型数据库 | 必需 | SQLite（内嵌，`modernc.org/sqlite`，无需独立进程） | Postgres 16 | `storage.database` |
| 向量库 | 必需 | ChromaDB（Python 内嵌，随 worker 一起启动，无需独立进程） | 本地 numpy+JSON（`local`，仅小规模库） | `storage.vector_store` |
| Embedding 服务 | 必需（上传书籍会调用） | OpenAI（`text-embedding-3-small`，需 API Key，按量计费） | Ollama 本地模型（`nomic-embed-text`，免费、无需联网） | `embedding.provider` |
| LLM 服务 | 仅「会话」问答功能需要 | OpenAI（`gpt-4o-mini`） | Ollama 本地模型（如 `llama3`） | `llm.provider` |

**SQLite + ChromaDB 是内嵌的，不需要额外部署任何东西**——这是本项目对 NAS/单机私有化部署场景的默认优化，详见 `docs/系统设计文档.md`。真正需要你额外决定「部不部署一个独立服务」的，只有 Embedding/LLM 这两项，以及可选的 Postgres。

## 3. 环境要求

### 方式一：Docker Compose（推荐）

- Docker Engine + Docker Compose v2（`docker compose`，不是旧版 `docker-compose`）
- 无需在宿主机安装 Go/Python/Node，构建都在容器内完成

### 方式二：本地原生开发（`make dev-up`）

- Go（`core-api` 用 `go run` 直接启动，无需提前 `go build`）
- Python 3.12+，并安装 `worker/requirements.txt` 依赖（建议用虚拟环境）
- Node.js 20+（`web-ui` 用 `npm run dev` 启动 Vite）

两种方式下，Embedding/LLM 依赖（OpenAI Key 或本地 Ollama）都需要单独准备，见第 5 节。

## 4. 部署步骤

### 4.1 Docker Compose

```bash
# 1. 按需修改 config/config.yaml（数据库、向量库、Embedding/LLM 提供方等）

# 2. 设置必要的环境变量（也可直接写入 config.yaml，二选一）
export OPENAI_API_KEY=sk-xxx
export JWT_SECRET=your-secret

# 3. 启动全部服务（默认 SQLite 后端）
docker compose up -d --build

# 若要改用 Postgres 后端：
STORAGE_DATABASE=postgres docker compose --profile postgres up -d --build
```

启动后：

- Web 管理后台：`http://localhost:3000`
- Core API：`http://localhost:8080`
- Worker（内部 gRPC，端口 8001，无需也无法用浏览器访问）：仅容器网络内可达

数据与配置通过 volume 持久化在宿主机 `./data`、`./config` 目录。`worker` 容器内存上限 1536M（ChromaDB 的实际需求）。

### 4.2 本地原生开发

```bash
make dev-up    # 启动 core-api / worker / web-ui，日志输出到 .tmp/*.log
make dev-down  # 停止
```

默认从 `config/config.yaml` 读取配置，SQLite 数据库位于 `data/mynexus.db`。

## 5. Embedding / LLM 服务部署

上传书籍后 worker 会调用 Embedding 服务做向量化——**这一步没有配置好会导致任务失败**（表现为任务状态 `failed`，错误信息类似 `HTTP Error 401: Unauthorized`，但书名/作者等元数据仍会正常写入，因为解析阶段先于向量化阶段完成，见第 7 节的说明）。

### 5.1 使用 OpenAI（默认）

`config/config.yaml`：

```yaml
embedding:
  provider: openai
  openai:
    api_key: "sk-xxx"           # 或用环境变量 MYNEXUS_EMBEDDING_OPENAI_API_KEY
    base_url: "https://api.openai.com/v1"
    model: "text-embedding-3-small"
llm:
  provider: openai
  openai:
    api_key: "sk-xxx"           # 或用环境变量 MYNEXUS_LLM_OPENAI_API_KEY
    model: "gpt-4o-mini"
```

Docker Compose 部署下，`OPENAI_API_KEY` 环境变量会同时注入 `MYNEXUS_EMBEDDING_OPENAI_API_KEY` 与 `MYNEXUS_LLM_OPENAI_API_KEY`（见 `docker-compose.yml` 里 `worker` service 的 `environment`），两个 key 目前是同一个值，若需要分开配置需直接改 `config.yaml`。

### 5.2 使用本地 Ollama（无需联网、无调用费用，适合本地测试）

Ollama 提供 Embedding（`nomic-embed-text`）和 LLM（如 `llama3`）两类模型，可以只用其中一个（比如 Embedding 走 Ollama、会话仍走 OpenAI），也可以两个都用。

#### 原生安装（macOS，推荐日常本机开发用，Apple Silicon 有 Metal 加速）

```bash
brew install ollama
brew services start ollama          # 或前台跑: ollama serve
ollama pull nomic-embed-text        # embedding 模型，~274MB
ollama pull llama3                  # 如需本地 LLM 问答，可选

# 验证
curl http://localhost:11434/api/embeddings -d '{"model":"nomic-embed-text","prompt":"test"}'
```

#### Docker 部署

> Docker Desktop for Mac 的容器跑在 Linux 虚拟机里，**没有 Metal GPU 直通**，容器内 Ollama 只能用 CPU，速度不如原生安装。对 `nomic-embed-text` 这种小模型影响不大，但本地 LLM（如 `llama3`）会明显更慢。

**独立容器**（配合本地原生开发 `make dev-up`：worker 跑在宿主机上，通过发布到宿主机的端口访问）：

```bash
docker run -d --name ollama -p 11434:11434 \
  -v ollama_data:/root/.ollama --restart unless-stopped \
  ollama/ollama

docker exec ollama ollama pull nomic-embed-text
```

`config.yaml` 的 `embedding.ollama.base_url` 保持 `http://localhost:11434` 不变即可。

**并入 `docker-compose.yml`**（worker 也在容器网络里时，需要用服务名而非 `localhost`）：

```yaml
services:
  ollama:
    image: ollama/ollama
    volumes:
      - ./data/ollama:/root/.ollama
    restart: unless-stopped
    # Linux 宿主机 + NVIDIA GPU 才需要，Mac 不用加：
    # deploy:
    #   resources:
    #     reservations:
    #       devices:
    #         - driver: nvidia
    #           count: 1
    #           capabilities: [gpu]
```

并把 `worker` service 加上 `depends_on: [ollama]`。**注意**：`config.yaml` 里 `embedding.ollama.base_url` / `llm.ollama.base_url` 目前没有对应的环境变量覆盖项（`worker/src/config.py` 只对 `api_key`、`internal_url` 做了 env 覆盖），容器化部署时需要直接把这两处改成 `http://ollama:11434`，不能像 `OPENAI_API_KEY` 那样通过 compose 的 `environment:` 传入——这是一个已知的待改进点，见文末 TODO。

拉模型：`docker compose exec ollama ollama pull nomic-embed-text`。

### 5.3 Ollama Embedding 模型选择

`embedding.ollama.model`（[config.yaml:56](../config/config.yaml#L56)）可以填 Ollama 库里任意 embedding 模型，向量维度是运行时读第一次调用的返回值动态确定的（`ollama_embedder.py` 的 `embedding_dimension()`），换模型不需要改任何代码。

| 模型 | 体积 | 中文效果 | 适用场景 |
|---|---|---|---|
| `bge-m3`（推荐） | ~1.2GB | 强 | 本项目默认面向中文书籍（`i18n.default_locale: zh-CN`，TXT 解析器专门识别"第X章"），中文语义质量优先时选这个。支持长文本（最长 8192 token），跟 `splitter.chunk_size: 500` 配合有余量 |
| `nomic-embed-text`（config.yaml 出厂默认） | ~274MB | 一般（以英文为主） | 书籍以英文为主、或只想先跑通流程验证功能时选这个，模型小、拉取快 |

```bash
# 原生安装
ollama pull bge-m3

# Docker
docker exec ollama ollama pull bge-m3
# 或 compose: docker compose exec ollama ollama pull bge-m3
```

配置：

```yaml
embedding:
  provider: ollama
  ollama:
    model: "bge-m3"   # 原来是 nomic-embed-text
```

**换模型注意事项**：不同 embedding 模型产出的向量不能混用（维度、语义空间都不同）。已经向量化过的书籍换模型后需要在后台「书籍管理」里执行「重建」/「批量重建」，重新生成向量；不重建的话旧向量还是留在向量库里，检索质量会明显下降甚至报错。

### 5.4 LLM 模型选择

`llm.provider`/`llm.openai.model`/`llm.ollama.model`（[config.yaml:33-42](../config/config.yaml#L33-L42)）驱动两个功能：管理后台的「会话」问答，以及**全书总结**（章节摘要 map + 全书总结 reduce，见 `worker/src/pipelines/summary.py`）——两者复用同一个 LLM 配置，没有单独的「总结模型」设置项。

#### 使用 OpenAI

出厂默认 `gpt-4o-mini`，兼顾效果和成本，一般不需要改。若对成本更敏感、且能接受长文本（全书总结的 reduce 阶段会把十几个章节摘要一次性拼进 prompt）效果打折扣，可以换成 `gpt-4o-mini` 的更便宜档位或其他 OpenAI 兼容服务（如 DeepSeek，把 `base_url` 换成对应地址即可，走的是同一套 OpenAI 兼容协议）。

#### 使用本地 Ollama

| 模型 | 体积/显存需求 | 中文效果 | 适用场景 |
|---|---|---|---|
| `qwen2.5:7b-instruct`（推荐） | ~4.7GB，建议 8GB+ 显存/统一内存 | 强 | 中文问答和总结质量都能打，是本地部署的首选起点 |
| `qwen2.5:14b-instruct` | ~9GB，建议 16GB+ | 更强 | 硬件允许时效果更好，但推理速度明显更慢 |
| `qwen2.5:1.5b-instruct` / `qwen2.5:3b-instruct` | 1-2GB | 弱 | 仅用于验证链路是否跑通（本项目开发时就是拿 `1.5b-instruct` 冒烟测试全书总结功能），不建议正式使用——参数量太小时全书总结容易出现复述不到位、甚至把 prompt 里的指令原样输出的问题 |
| `llama3`（config.yaml 出厂默认） | ~4.7GB | 较弱（以英文为主） | 书籍以英文为主时可以用，中文场景建议换成 `qwen2.5:7b-instruct` |

```bash
# 原生安装
ollama pull qwen2.5:7b-instruct

# Docker
docker exec ollama ollama pull qwen2.5:7b-instruct
# 或 compose: docker compose exec ollama ollama pull qwen2.5:7b-instruct
```

配置：

```yaml
llm:
  provider: ollama
  ollama:
    model: "qwen2.5:7b-instruct"   # 原来是 llama3
```

**上下文长度提醒**：全书总结的 reduce 阶段会把全部章节摘要一次性发给模型，章节数多的书可能超出模型的默认上下文窗口；Ollama 模型的上下文窗口默认较小（很多模型默认只有 2048~4096 token），如果总结经常被截断或报错，需要在 `Modelfile` 里调大 `num_ctx` 后 `ollama create` 一个自定义 tag，或换成上下文窗口更大的模型变体。

### 5.5 切换 provider

```yaml
embedding:
  provider: ollama   # openai | ollama
llm:
  provider: ollama    # openai | ollama，跟 embedding 是两个独立开关
```

改完 `config.yaml` 后需要重启 `worker`（原生开发：`make dev-down && make dev-up`；Compose：`docker compose restart worker`）。

## 5.6 后台「系统配置」页面（免手改 config.yaml）

管理后台的 Drawer →「设置」分组 →「系统配置」页面可以直接编辑本文档第 5 节涉及的所有配置项（以及 storage/worker/splitter/i18n/chat），不需要登录服务器改 `config.yaml`。对应 API 是 `GET/PUT /api/v1/system/settings`（`server`/`auth` 两段除外——JWT secret 等进程身份/安全类配置不通过这个页面改）。

**保存后的行为**：

1. 整个 `config.yaml` 会被结构体重新序列化写回——**手写的行内注释会丢失**，这是当前的已知取舍（换来实现简单可靠），文件里的值本身不受影响。
2. core-api 写完文件后，会尽力（best-effort）调用 worker 的 gRPC `Shutdown`，再自己 `os.Exit(0)` 退出进程，让两边都用新配置重启：
   - **Docker Compose 部署**：`restart: unless-stopped` 会自动把两个容器重新拉起，全程不需要人工干预。
   - **本地 `make dev-up` 开发**：`go run`/`python3` 直接跑的进程退出后不会自动回来，需要你手动再执行一次 `make dev-up`。
3. core-api 的登录会话是进程内存里维护的（见第 8 节），进程一重启，当前登录状态就没了，页面会在保存成功后自动跳回登录页，需要重新登录。

## 6. 数据库选择

见 `README.md` 的「后端数据库选择」一节，此处不重复：`storage.database` 支持 `sqlite`（默认，零运维，适合 NAS/单实例）与 `postgres`（更强并发写入，适合多实例）。

## 7. 已知问题与排查

- **SQLite `database is locked (SQLITE_BUSY)`**：已在 `core-api/internal/storage/sqlite/sqlite.go` 通过开启 WAL 模式 + `busy_timeout` + 限制单连接解决，无需额外配置。
- **上传书籍任务失败、错误信息是 `HTTP Error 401: Unauthorized`**：Embedding provider 没配置好（见第 5 节），不是文件本身的问题。书籍的标题/作者是在解析阶段（早于向量化）就写回数据库的（`ReportMetadata` gRPC 调用），所以即使向量化失败，书名/作者依然会正确显示——如果书名作者也是空的，说明文件解析本身失败了（文件损坏或格式不支持），需要看 `worker` 日志（`.tmp/worker.log` 或容器日志）里的具体异常堆栈。

## 8. 默认账号与安全提醒

首次启动自动创建管理员账号 **`admin` / `admin`**，仅在 `admin_users` 表为空时播种一次。**首次登录后请立即在「设置」页面修改密码**。生产部署务必修改 `auth.jwt_secret`（或环境变量 `MYNEXUS_AUTH_JWT_SECRET`），不要使用默认值。

## 9. 数据持久化

`./data` 目录下：

- `mynexus.db`（+ `-wal`/`-shm`）：SQLite 数据库
- `uploads/`：原始上传文件
- `vectorstore/`：ChromaDB 数据

备份时把整个 `./data` 目录连同 `./config` 一起打包即可。
